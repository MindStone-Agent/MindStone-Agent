# Changelog

Everything that ships to `main` is recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/). Dates are UTC.

Every pull request to `main` adds its entry under **Unreleased**. A release moves those entries into a versioned section and tags `main`.

## [Unreleased]

### Added
- **Every setup choice has a settings equivalent** (#140). See `docs/gateway/API_REFERENCE.md`.
  - `GET/PATCH /admin/user`: the Console's Settings reads and replaces what the agent knows about the owner (the default agent's `USER.md`). A write needs advanced settings and the strong etag read with it, so it is refused when the file changed since it was read (the agent updates it too); only a plain file named `USER.md` with one name (no symbolic or hard link) under the `agents/` folder next to the config is read or written, so a `userPath` pointed at a stored secret reads nothing. New smoke: `scripts/smoke-user-md.sh`.
  - **Changing the embedding model no longer mixes models in recall.** Recall compared a query with every stored vector, truncating the longer one, so after a switch old memories got meaningless scores (and two models of the same size were just as wrong). Each chunk now records the model that embedded it; recall uses only chunks the current model embedded and finds the rest by their words; the backfill (including the one after each owner turn) embeds the others again. Vectors from before this change count as another model's and are embedded again once. `POST /admin/memory/check` reports `index: { embedded, otherModel }`. Re-embedding doesn't change a chunk's time, so the newest chats stay first in recall's window on a large index. After a switch (or on upgrading) each owner turn's index update embeds that turn's own chunks, then at most 128 of another model's, newest first, so what is said meanwhile is recalled at once and the rest are embedded again over the following turns; `mindstone memory backfill --embed` does them all at once. A vector is only written if the chunk's text is still the one embedded. New smoke: `scripts/smoke-memory-model-switch.sh`.
  - **The memory check waits for a model to load.** Its own embed gets 45 s (a chat's stays at 10 s): `mxbai-embed-large` took about 13 s to load, so the check always failed on a cold model. A timed-out check says so with its limit; a long upstream error is cut to 300 characters; an `EMBEDDER_TIMEOUT_MS` that isn't a positive number counts as the default.
  - Enterprise endpoints list their other sign-in options as `planned` (Entra ID or managed identity, an IAM role or access keys, workload identity federation). They aren't available yet, and a value for one is refused.
- **Knowledge bases are recalled by meaning** (#125, part 5). With an embedder configured (`memory.embeddingProvider`), `kb ingest` (global and private KBs, CLI and admin API) embeds each entry and writes `vectors.json` beside `index.json`, with the provider, model, dimension and the index's sha256. Ingest never fails because of it: with no embedder, a failure or past 120 s, the index is written, old vectors are removed, and recall uses word match. `kb status` reports `vectors` (`ready`, `missing`, `stale` with "re-ingest" after a provider, model or index change, `unused`). At recall the question is embedded once per turn, shared with memory recall; KB sources are ranked by their best entry's cosine (showing their 5 closest sections) and take their own slots, out of `memory.recall.maxResults` (memory keeps at least one when it has a hit of its own, any hit not from a knowledge base, so with `memory.recall.maxResults: 1` memory's hit wins, #151; `knowledgebaseRecallSettings` is exported from core), and share the recall token budget with memory (when there is a slot for each, the best of each always goes in, even past the budget; other KB sources up to half of what is left, then memory, then any budget left). Approving an agent-proposed private KB embeds it too, after the admin write lock is released (`knowledgebases.recall.maxResults`, default 3; `minSimilarity`, default 0.5, in place of memory's `minScore`). Word match still runs for every source. Vectors of another dimension, or an embedder that is down, fall back to word match. An embedder that returns an all-zero vector fails that KB's embedding (#151), and an all-zero question vector recalls nothing by meaning. `vectors.json` is read only on a turn that ranks by meaning, cached while the file stays the same (512 MB in all), and not above 256 MB. Ingest embeds 8 entries a request (60 s each, retried an entry at a time), within 120 s or `kb ingest --embed-timeout <seconds>`. Entry ids are made unique when headings slug alike (a `~2` suffix). **KB embedding runs whenever an embedder is set** (`memory.embeddingProvider`, or `MINDSTONE_EMBEDDING_PROVIDER` / `EMBEDDING_PROVIDER` in the environment), even without `sqlite-vec`: KB text and questions then go to that embedder. See `docs/operations/KNOWLEDGEBASES.md`.
- **Build personas, workflows and private knowledge bases from the admin API** (#125, part 2). See `docs/gateway/API_REFERENCE.md`.
  - **A private KB's URLs reach public hosts only** (#142 review): never this machine (any of its addresses), a private, reserved or link-local network or metadata address; refused when added and when fetched (by resolved address, on every redirect, at most 5), connecting only to the checked addresses; HTML, markdown or plain text only. In the gateway host's environment, `MINDSTONE_KB_PRIVATE_HOSTS=1` allows private networks (still never this machine, link-local or metadata addresses) and `=any` also allows this machine (test stubs), never link-local or metadata. `kb ingest --persona` applies the same rules; a global KB's URLs are fetched as before. `isNonPublicHost` (also used for enterprise endpoints) now also refuses 6to4 and NAT64 addresses carrying a private IPv4, NAT64 local-use, Teredo, site-local, 192.0.0.0/24 and 168.63.129.16.
  - **An HTML page is read in linear time.** The extractor no longer uses backtracking patterns: a page built to be slow (`<title>` repeated) held the gateway's event loop for tens of seconds.
  - **A persona that doesn't load gets no skills and no KBs** on its turns, instead of every skill and every collection, and says so (`loadFailed`; the load error is written only to an owner's transcript). A list file must be a list of non-empty ids, or `{"<name>": [...]}` with only that key; any other shape makes the persona fail to load, a pack carrying one is refused at install, and a workflow step's `skills` or `knowledgebases` of the wrong shape makes the workflow fail to load (it is skipped, so that turn uses the persona's own lists without the step's narrowing). A persona id must be a folder name.
  - `GET/POST /admin/personas`, `GET/PATCH /admin/personas/<id>`: a persona's text and its skills, workflows and global KB collections, each checked to exist. Saving never activates it. New ids follow #105's rules (lowercase, not on disk in any case, not used by the config).
  - `GET/POST /admin/workflows`, `GET/PATCH /admin/workflows/<id>`, with strict checks: unknown keys, empty conditions and empty gates are refused, `retry.maxAttempts` is 1 to 5, and a step's persona must exist under exactly that id.
  - `GET /admin/knowledgebases` lists the global collections. `GET/POST /admin/personas/<id>/knowledgebases`, `…/<kb>/sources` and `…/<kb>/ingest` build a persona's private KBs: markdown text sources, and URL sources, which need the advanced-settings permission to add and to ingest (a URL with a user name or password is refused). A fetch from the admin API is capped at 20 s and 5 MB, 10 URLs per KB, one ingest per KB and two at once.
  - A workflow id the config already runs, or a persona already lists, can't be created (`409 workflow_referenced`); a route step's skills must be installed. `GET /admin/workflows/<id>` returns the shape `PATCH` takes.
  - **KB citations, recall text and fetch errors write a URL source without its query** (for global KBs too): no user name or password, no query or fragment (shown as `?…`), no matrix parameters, and a path segment that may be a credential as `***`. The fetched address is unchanged. A citation that relied on a query to tell pages apart now shows `?…`.
  - Packs: a persona's private KB is held to the packed-KB rules (only `kb.json` and `sources/**`, no `externalSources`), in any casing.
  - Creates are staged in a dot folder and moved into place; persona, workflow and KB discovery skip dot folders. An edit checks every file it writes before changing any, and keeps what `metadata.json` held. Links are refused. Every write is audited.
  - New smoke: `scripts/smoke-persona-admin.sh`.
- **The agent proposes a persona with its components** (#125, part 3). A `mindstone-persona-proposal` can list existing skills, workflows and shared KBs, and bring up to 3 new skills, 3 new workflows and 2 new private KBs (markdown text sources). Each new one is its own approval card, linked to the persona's: it can be approved only after the persona, and rejecting the persona rejects it. An approved component joins its persona; a proposed private KB is written and ingested. A proposed workflow can't hand the turn to, or gate on, a persona. A proposal whose components don't hold up, or that would pass a pending cap (6 component cards per kind), is dropped whole, and the reply says why. `mindstone approvals show` and the approve prompt show a persona's components and each component card in full. The owner's instruction and the persona footer now say a persona sets voice, working style and its components. New smoke: `scripts/smoke-persona-proposal-components.sh`.
  - A component card attaches only to the persona its own persona card wrote: the approved persona's `metadata.json` records that card's id, and a persona removed and made again under the same id refuses the old cards (`invalid_persona`).
- **Persona follow-ups** (#125, from #141's review): a persona whose `skills.json`, `workflows.json` or `knowledgebases.json` doesn't parse now fails to load, like a bad `metadata.json`, instead of reading as "every skill" or "every collection"; a persona's private KBs are used only under the id its folder has on disk (a case-insensitive filesystem finds `Persona-Two` for `persona-two`); an edit can clear a persona's description (`"description": ""`); a workflow gate that never passes records the attempts it made (it said one more).
- **A persona's components take effect** (#125, part 1). While a persona is active, its skills, workflows and knowledge bases are the ones in play; see `docs/operations/PERSONAS.md`.
  - **Skills:** only the skills in its `skills.json` go into the owner's prompt; with none listed, all installed skills do, as before. A listed skill that isn't installed is skipped and recorded. **A persona pack's existing `skills.json` now restricts the prompt to those skills, and its `knowledgebases.json` restricts recall to those global collections** (for example, a pack persona listing one collection no longer searches the others).
  - **Global knowledge bases:** only the collections in its `knowledgebases.json` are searched; with none listed, all of them.
  - **Private knowledge bases:** a persona can own KBs under `personas/<id>/knowledgebases/<kb-id>/`, in the global format. They are searched only while that persona is active, on owner turns and tenant App Engine runs, never under another persona. Recall ids are `pkb:<persona-id>:<kb-id>:<source>`. Symbolic links in them (the persona folder, the KB folder, `kb.json`, `index.json`, sources) aren't used. `mindstone kb list|ingest|search|status --persona <id>` manage them.
  - **Workflows:** every workflow in the persona's `workflows.json` is a candidate, in order (it was only the first); the first to decide is used, and a `stop` gate ends the selection. A persona named by an App Engine request uses its own workflows. A step that routes to another persona brings that persona's components; a step's `skills` now narrow the skill set and its `knowledgebases` narrow global and private KBs each on its own (they were only logged). **With no persona active, a step's lists are still only logged.** `retry.maxAttempts` is capped at 5.
  - Each assistant entry and native chat response records `personaComponents` (left out for non-owners). The Console's Skills page marks a skill the persona in `personas.active` leaves out as not in the prompt. A step's KB ids that match no KB are recorded as `stepKnowledgebasesUnknown`.
  - New smoke: `scripts/smoke-persona-components.sh`.
- **Enterprise model endpoints** (#126): Azure OpenAI / AI Foundry, Amazon Bedrock, Google Vertex AI and an OpenAI-compatible enterprise gateway, set up from the Console.
  - `POST /admin/providers/enterprise/<kind>` registers one from stored secrets, with the provider-key guards (#80): never a gateway credential or a connector's token, never echoed or audited. Addresses are https to a public host; the gateway host can allow private-network hosts with `MINDSTONE_ENTERPRISE_PRIVATE_HOSTS=1`.
  - Each provider's key and settings go to Pi's isolated `auth.json` for that provider only, and Pi reads them before the gateway's environment. Bedrock takes a Bedrock API key, which Pi sends ahead of any `AWS_BEARER_TOKEN_BEDROCK` in the environment; access keys aren't supported (Pi sends a Bedrock provider's stored key as its bearer token). A Vertex API key Pi would read as "use this machine's Google login" is refused. A Vertex service account key is reduced to a plain service account and copied to a file the gateway owns, so replacing the secret later changes nothing Google's client reads. Re-registering replaces the provider, so nothing from an earlier address follows it.
  - Requests to a registered Azure or gateway address never follow a redirect: chats and Tests from the gateway, `mindstone chat` and the TUI (a guard on the fetch Pi's clients use), the model listing and embeddings. Pi run on its own (`scripts/pi-agent`) isn't covered. An address is checked by its name, not by what it resolves to. Bedrock goes to AWS's own address for the region (or for the region in an inference-profile ARN model id) from the gateway, `mindstone chat` and the TUI, which ignore AWS endpoint settings on the host (`AWS_ENDPOINT_URL*`, `endpoint_url`), for everything they start too, the agent's `bash` tool included; `scripts/pi-agent` still follows them.
  - `POST /admin/providers/<id>/test` sends one short message through Pi and reports the answer or the error, with the provider's secret values redacted. `DELETE /admin/providers/<enterprise provider>` removes one.
  - Memory can embed through a registered Azure or enterprise gateway endpoint (`enterprise-azure:<deployment>`, `enterprise-openai:<model>`), with its own address and key.
  - New smoke: `scripts/smoke-enterprise-endpoints.sh`.
- **Recall carries one chat into the next** (#106). With automatic recall on, a fact the owner tells the agent in one Console chat is recalled in a new chat, with no manual backfill.
  - **Automatic recall is on by default, and a missing `memory.autoRecall` now means on.** This includes existing installs whose config has no `autoRecall` key: they start recalling, and indexing their chats, after the upgrade. Set `"autoRecall": false` to keep it off. The installer, `mindstone onboard`, the configure wizard and the Console's setup all start with it on. Turning it off needs no permission; turning it back on, or removing the key, needs the advanced-settings permission.
  - While recall is on and `memory.vectorStore` is `sqlite-vec`, the gateway indexes each turn's transcript (and new or changed memory files) into the recall index in the background after the reply, and embeds the new chunks, newest first. With an external embedding provider (`openai:`), that sends each owner chat to the provider. With recall off, nothing is indexed or embedded; `mindstone memory backfill` indexes earlier chats on request.
  - Updates run one at a time. A failed update is logged and retried with the next turn. Recall waits briefly (up to 5 s) for queued updates, and not at all within a minute of a failed one. Chunks not embedded yet are still found by their words, so a fact from the last turn is recalled even while the embedder is down.
  - Console and REST turns now record `ownerTurn`. Nothing written for a Console user is indexed into the owner's recall, whatever its role, including older transcripts, recognized by their non-owner session key (which now keeps its `non-owner` prefix for long user ids). A Console user's `/v1/responses` input keeps only its user items.
  - A tenant's App Engine run never recalls the owner's chat transcripts (their unscoped memory files are still #71).
  - Recognizable credentials (API keys, tokens, private keys, JWTs) are masked in chat text before it is indexed. A client's system prompt is not indexed.
  - The runtime's bookkeeping events (recall, index and invariant injections, identity formation, handoffs, pruning, compaction, routing, workflow, persona switch and approval notices) are no longer indexed, so recall can't feed on itself. Tool activity stays recallable.
  - Memory files and knowledge come before chat transcripts in the recall index's candidate set, so a long chat history can't push MEMORY.md out. Knowledge-base documents are searched next to the recall index, as they were before the index existed.
  - The recall event records a SHA-256 of each hit's text and where it came from, and the assistant entry records `memoryRecall` (query, hit count, prompt tokens, chunk ids). The recall usage log moved from the memory folder to `<dataDir>/logs/recall-usage.jsonl` (an existing file is moved on first use), since it holds the owner's queries.
- **The agent proposes its own persona, approved in the Console** (#105).
  - In an owner's turn, the agent can end a reply with a `mindstone-persona-proposal` block. It holds an id, name, description, voice, working style and boundaries, each with a length cap. The block is stripped from the reply and becomes a pending `persona_create` approval. A Console user's or connector non-owner's block is dropped. The owner's turns carry a short instruction describing the format, and identity formation now ends by proposing one.
  - Approving it (Console or `mindstone approvals approve`) writes `personas/<id>/PERSONA.md` from a fixed template (Voice, Working style, Boundaries; headings in the proposal's text stay text) and `metadata.json`, and adds it to the Personas list. It does not make it active: switching to it is a separate, deliberate step (the Console's Personas page, `PATCH /admin/config/personas`, or `mindstone persona activate`). An existing id, or anything already at that path, is refused (`409`) and the approval stays pending. Rejecting writes nothing.
  - A proposal with characters the approver can't see (controls, bidi overrides, zero-width or tag characters) is refused, and code fences, setext headings and HTML comments in its text are quoted, so the approval card shows everything the persona holds. `mindstone approvals show` and the approve prompt show the persona as it will be written. At most 3 persona proposals wait at once.
  - `GET /admin/personas` lists the personas and the active one. Switching is the existing `PATCH /admin/config/personas`.
  - Approving never makes a persona active: an id the config already uses (`personas.active`, a route rule, a workflow step), in any case or any form the filesystem folds to the same directory, is refused with `409 persona_referenced`. Each assistant transcript entry records the persona that answered; a non-owner's response doesn't include it.
  - The instruction tells the agent that a persona is used in every chat, other people's and connectors included, so private details about the user stay in USER.md.
  - A proposal counts only as a top-level block: one shown inside another fence (an example, or the instructions echoed back) stays in the reply as text. A character with three or more stacked combining marks is refused. App Engine runs never propose a persona.
  - New smoke: `scripts/smoke-persona-proposals.sh`.

### Changed
- **Knowledge bases follow a switch of embedding model** (#151). After an owner chat through the gateway, one KB whose vectors another model made (global or private, at most 512 entries) is embedded again from its current index in the background, as memory's chunks are (#140): its entries go to the new embedder with no ingest by anyone. A larger KB, or one whose index changed while the model stayed the same, still needs `kb ingest`; a failed attempt keeps the old vectors and is retried after 30 minutes, doubling each time, and not again for that model after five failures until the gateway restarts; an ingest that rewrites the index meanwhile keeps its own vectors and isn't counted as a failure. The KB re-embed sends one entry a request and starts none while a chat turn runs, so on an embedder that answers one request at a time it slows an owner's turn by one entry at most (memory's own backfill after a switch, #140, is not paced this way yet); on a gateway that is always answering it waits for a gap. Each attempt is audited as `kb_reembedded`. KB word-match hits carry `recallMode: "lexical"`, and KB vectors are matched with memory's `<provider>:<model>` spec (`memoryEmbeddingSpec` now lives in `memory/embedding.ts`, still exported from core).
- **Proposals outside personas, changed by #125 part 3:**
  - **Plain skill proposals** (`mindstone-skill-proposal`) refuse, in every field, control, format, private-use and unassigned characters, default-ignorables, line and paragraph separators, the braille blank, Hangul fillers and 8 or more combining marks in a row. Zero-width joiners, variation selectors and U+180E stay allowed only where real writing puts them: a joiner between two non-ASCII characters (emoji sequences, Persian, Indic), never two in a row and never next to a space or ASCII; an emoji selector after an emoji (after a digit, `#` or `*` only as a keycap); U+FE00 after Han, Myanmar or a non-ASCII math symbol; U+180E between Mongolian characters. Other selectors (U+FE01–FE0D, ideographic selectors such as Japanese name variants, and Mongolian's free variation selectors U+180B–180D and U+180F) are refused. Eight or more combining marks in a row, counted through joiners, is refused. The label and description must be one line: a proposal with a multi-line description, accepted before, is now dropped. **The same rules apply to an admin's skill draft** (`POST /admin/skills/drafts`): pasted text with a soft hyphen, a byte-order mark or a direction mark (common in mixed Hebrew or Arabic and English) is now refused with a 400 that says so, from scratch or over a built-in.
  - **A dropped skill or persona proposal is noted in the reply**, with a fixed reason, instead of disappearing silently. A dropped memory or connector proposal is still dropped without a note.
  - **Memory paths and calendar or other connector resources** in proposals must be one line with no invisible or directional characters; such a proposal is dropped.
  - **The CLI shows invisible characters as `\u{..}`** in `approvals show`, the approve prompt, card summaries, KB lines and `skill list`.
- **Pi updated from 0.79.4 to 0.87.1** (#127). The vendored Pi (`vendor/pi`) is upstream v0.87.1, and `@earendil-works/pi-coding-agent` in the lock matches. What changed for MindStone:
  - Models and provider auth now go through Pi's `ModelRuntime`. The gateway's Pi provider and the pi-session runner build it from the install's own `auth.json` and `models.json` (never Pi's global files) with no catalog fetches at run time, and sessions use the same runtime. The Pi provider completes through the runtime, so a provider's resolved base URL applies.
  - `mindstone auth` OAuth login uses Pi's new login flow (`ModelRuntime.login`). The `auth.json` format is unchanged; `$ENV_VAR` references still resolve.
  - Pi added a built-in `powershell` tool. It is off, like the other built-ins that aren't enabled.
  - The CLI TUI uses Pi's `TuiMainScreen` renderer.
  - **Model lists:** upstream no longer commits its model data. MindStone keeps it in the repo (`vendor/pi/packages/ai/src/providers/data`, hydrated from public catalogs on 2026-09-28), so install still builds offline from reviewed lists. `npm run build` in `vendor/pi` builds without fetching; `build:regen-models` refreshes the lists first, and `npm run hydrate:model-data` refreshes the data alone.
  - Pi 0.87 ships the Azure OpenAI (Responses), Amazon Bedrock and Google Vertex providers that #126 builds on.

### Fixed
- **A KB re-embed no longer gives up because of a cheap outage, and its state survives a restart** (#158). A 429 is now a pause: the job waits (Retry-After, 30 seconds to 5 minutes, off its budget) and sends the entry again, up to 5 times. Only a failure that cost nothing is free (nothing embedded, and the embedder out of reach, down, without a key or model, timed out, or still answering 429): it waits 30 minutes, however often. Anything else counts toward giving up, including a failure after some entries were embedded and vectors that couldn't be written. The state (failures, next attempt or given up, last reason) is kept in the KB's `reembed.json`, so a restart doesn't grant more tries; a state for another model doesn't apply, and it is removed once the KB is embedded for the install's model. `kb status` shows it, and `GET /admin/knowledgebases` and a persona's KB lists carry it as `reembed`, for the Console. The audit entry carries `cause`. A turn running more than 10 minutes no longer holds the re-embed back. The embedding provider's errors now carry the HTTP `status` (and a 429's `retryAfterMs`), and a server it can't reach is marked `unavailable`.
- **Hidden CLI prompts: escape sequences, pasted text and Ctrl-D** (#133).
  - Escape sequences such as arrow keys are skipped whole, even when they arrive split across input chunks, so no `[A` ends up in a key.
  - A bracketed paste keeps its text, with line breaks removed.
  - Input that arrives within 40 ms after Enter (the rest of a multi-line paste, or the LF of a split CRLF) is discarded instead of becoming the next answer.
  - Ctrl-D on an empty prompt now cancels it, like Ctrl-C. It used to submit an empty value, which made the wizard skip auth.
- **A Console chat runs on the model chosen in setup** (#126 J11, #118). The Console sends `model: "mindstone/default"`, which reached Pi as an unknown model id and silently fell through to the first available provider. So with more than one provider configured, chats ignored the setup's choice.
  - `mindstone/<agentId>` now names an agent, meaning that agent's model.
  - An agent's own `agents.<id>.defaultModel` now beats the install's `routing.defaultModel`.
  - A non-owner turn (a Console user, a connector's non-owner, a tenant run) can't choose the model; it gets the agent's.
  - When Pi doesn't know a requested model, the session executor and the Pi provider use the configured default before the first available one, and log either fallback.
  - New smoke: `scripts/smoke-model-selection.sh`.
- **Hidden CLI prompts handle a pasted key and Ctrl-D** (#131). A key pasted together with its newline now submits, without a trailing `\r` (which Pi login secrets kept). Ctrl-D ends the prompt instead of adding `\x04`, other control keys are ignored, and an arrow key's escape sequence is dropped.
- **Secrets typed at the CLI are no longer shown on screen, and Pi's cache warming stays off** (#129).
  - A hidden prompt, such as the wizard's API-key prompts or a login's secret prompt, closes the prompter's readline while it reads, since a real terminal echoed the secret even with the readline paused. New pty smoke: `scripts/smoke-cli-secret-echo.sh`.
  - Only `off`, `streaming` or `idle` in the Pi agent dir's `settings.json` counts as a cache-warming choice; any other value is replaced with `off`, because Pi would fall back to `streaming`. `init-runtime.sh` now seeds `off` too, so `scripts/pi-agent` doesn't warm the cache before the first gateway turn.
- **Console setup reaches a working agent, and only admins are the owner in Console chats** (#102, #103).
  - **Identity formation now runs in Console chats.** `/v1/chat/completions` never called the first-activation identity-formation prompt, so a Console-only install never started it, even after `mindstone onboard`. The owner's first Console conversation after setup now starts it, once per agent rather than once per conversation. It waits until setup has finished.
  - **`POST /admin/onboarding/complete`** finishes the Console's setup as `mindstone onboard` does: the onboarding record and the IDENTITY.md/USER.md scaffold, from the same core code. A placeholder is replaced with a backup; a real file is kept.
  - **The memory step:** `POST /admin/memory/check` runs a live embed with the provider about to be saved, and `POST /admin/memory/pull` downloads a missing Ollama embedding model.
  - **The checklist:** `/admin/status` now says `onboarded` only with a provider, a persona, memory (a vector store and an embedding provider) and the identity scaffold. Memory is required, and says what's missing; a new `identity` step; connectors stay optional.
  - **Owner audience (#103):** a Console `user`, or a blank role header, now gets the non-owner context: no USER.md, memory index, autoRecall, owner-only invariants or handoff. Before, every Console user got the owner's. A Console admin, and a direct caller with the service token and no role header, are still the owner.
  - `onboarding.identity.mode` is validated (`defer`, `seed` or `custom`).
  - The identity scaffold keeps the user's own words (purpose, preferences, project context) in USER.md only; IDENTITY.md, which non-owner turns also get, carries only the profile's seeds. This applies to `mindstone onboard` too, and to the identity `mindstone identity activate` writes: it keeps the chosen preference labels, points at USER.md for the notes and project context, and no longer names host paths. The first-chat formation prompt puts each onboarding seed on one line, so typed text can't start a heading of its own. `memory/pull` only fetches the model the last check reported missing. `/v1/responses` now decides the owner the same way chat completions does; before, it always ran as the owner, so a Console user could reach the owner's context once Responses was switched on.
  - **Upgrading:** an existing install that has only a provider and a persona now reports `onboarded: false` until memory has an embedding provider (the environment's `MINDSTONE_EMBEDDING_PROVIDER` counts) and setup has finished. The Console's setup banner comes back until then. Deploy this with the Console's matching setup change (mindstone-console, the same #102). The gateway never sends an agent that already has a real IDENTITY.md back to identity formation (`mindstone chat` in the CLI still prompts formation on a new session, as before).
  - A Console user can no longer reach another session: `metadata.sessionKey`, `metadata.agentId` and the body's `user` are ignored for a non-owner, and a non-owner without a conversation id gets a session of its own rather than the owner's main one. A non-owner turn without a forwarded user id is refused (`400`), and a user's non-owner sessions are kept apart from the same user's owner-audience ones. `memory/pull` only takes model names from Ollama's default registry.
  - New smoke: `scripts/smoke-console-onboarding.sh`.
- **A Console-first install no longer needs the terminal wizard** (#108). `install.sh` (through `npm run install:native`) now creates `.runtime/mindstone/config.json` on a first install, with `scripts/init-runtime.sh --if-no-config`: not onboarded (`routing.mode: placeholder`), the gateway on `127.0.0.1:19789` with auth `none`, and placeholder identity and user files. The config validates, `mindstone doctor` and `status` work on it, and `GET /admin/status` reports `onboarded: false`, so the Console's setup banner shows and guided setup finishes onboarding. An existing `config.json` is never touched: a re-run of the installer, which is also the update path, leaves a configured install as it is.
  - The created config sets no `routing.defaultModel`, so `mindstone onboard` (and `install.sh --onboard`) over it defaults to "Leave unset" rather than a `mindstone/default` model that doesn't exist. `init-runtime.sh` no longer writes through a `config.json` symlink, even a dangling one, and never replaces a config created while it runs.
  - `mindstone chat` on a not-yet-set-up install points to `mindstone onboard` (or the web Console) again, as well as `mindstone config --section routing`.
  - The README's install guide for AI agents now has two onboarding paths in step 2: (a) `mindstone onboard` in a terminal, or (b) skip it and set up in the web Console (steps 3 and 5, then the Console README). Step 5 no longer requires 2(a), and step 5.4 says `routing.mode: placeholder` is expected on a Console-first install.
  - Step 3 documents how to change the gateway port: `MINDSTONE_AGENT_GATEWAY_PORT` moves the listener, `gateway.port` in `config.json` is what the CLI's health checks use, and the two must agree.
  - `install.sh` writes its status check to a per-run temporary file that it removes, instead of the fixed `/tmp/mindstone-agent-install-status.txt`, so installs running at the same time don't overwrite each other.
- **The advanced-settings confirmation no longer has to be typed exactly** (console #18). `POST /admin/permissions/advanced` refused `Enable advanced settings` (a phone capitalizing the first letter) and a trailing space from autocomplete. It now ignores case, surrounding whitespace and repeated spaces, but the words must still be `enable advanced settings`; anything else is still a `400`. The admin smoke covers both.
- **The installer failed on a fresh machine.** Building Pi regenerated its model lists from the providers' live APIs on every install. When a provider added a field Pi doesn't know, the generated file stopped compiling and the install died in `npm run install:native` (it did on 2026-09-27). The build now uses the committed model lists; `npm run build:regen-models` in `vendor/pi/packages/ai` regenerates them on purpose. Re-running the installer restores the committed model lists and npm lockfiles before pulling, so an earlier install can't block the update or break the build.
- **`install.sh --no-link` left the CLI unbuilt**, so `./node_modules/.bin/mindstone` said "not built yet" and the installer stopped at its own status check. It now builds the CLI in place.
- **Stored-secrets follow-ups** (#92). `GET /admin/secrets` no longer reports a secret's size. Deleting or storing a secret is refused if the config can't be loaded at that moment, instead of going ahead without knowing the gateway's own credential files. The Console hides Delete for names the gateway would refuse.
- **Admin API follow-ups from the #75 review** (#78).
  - A new secret could be planted into a file that didn't exist yet but that a connector reads, or into one of the gateway's own credential files, under another name: through a chain of dangling links, or a name the filesystem folds to it (APFS treats `ß` as `ss` and `ſ` as `s`). A new secret is now created exclusively, and if a protected file that was missing exists afterwards, the new secret is removed and refused: `403` for a connector's file without the permission, `422` for a gateway credential whatever the permission. The gateway credential check also follows symlinks, a secret name that is a link made on the host is never replaced, and a new secret is created with an exclusive open (no hard-link support needed).
  - A secret write that fails (the name is a directory, for example) no longer leaves the value in a temporary file.
  - An admin API `500` is audited with the user id.
  - `GET /admin/permissions` shows the expiry that applies (at most an hour after the grant), not a later one from the stored file.
  - Removing `memory.autoRecall` (which turns it off) no longer needs the permission. Removing a channel's `enabled`, which turns it on, still does.
  - The smoke now covers the config file living outside the data dir, turning autoRecall off after it was on, and the audited `500`.
- **Chat completions no longer store the whole conversation again every turn** (#38). Clients such as LibreChat resend the full history with each request, and the gateway wrote all of it to the transcript each time. Only the new turn (the trailing user messages) is stored now.
  - **Breaking:** a request that doesn't end with a user message (for example a tool-role or assistant-prefill tail) is now a 400. A message with no role counts as a user message.
  - Client system prompts: ignored for the Console's `user` role (logged once per session as an event), stored once per session for an admin or a direct API caller. Before, every resent copy was stored.
  - Each Console conversation (`x-mindstone-conversation-id`) gets its own session, so separate chats don't share a context window. Switching persona mid-conversation keeps its history. The memory backfill indexes every conversation into memory. Recall isn't yet scoped per agent or per Console user (#71).
  - The gateway replays the auto-compact handoff only into the session that wrote it, not into every new session (the CLI and TUI are unchanged). In `per_surface` mode, one surface's handoff no longer carries over to another surface's session.
- **Connector replies: no lost updates or double sends between drains, retries with backoff, and no error text in chats** (#63).
  - A reply queued while the queue was being drained could be overwritten and never sent. Every queue change is now a locked read-change-write, including enqueues from the CLI when an approved send is released.
  - A queue file that can't be read (permissions, I/O) or doesn't parse is no longer treated as empty and overwritten. Reads report it: `mindstone status` shows the queue as UNREADABLE, and the Gateway logs it. A write stops with an error; under the lock, a corrupt file is first moved aside as `queue.json.corrupt-<time>`, so the next write starts a new queue. Writes are fsynced.
  - A reply the queue refused (locked, I/O error, unreadable file) was dropped with nothing in the Gateway log. It is now retried in the Gateway for about 13 minutes, with each failure logged, then drained. A Gateway restart during the retries, or running out of them, loses it, and that is logged too. Drain errors are logged instead of ignored.
  - The per-message drain and the periodic drain could both send the same reply. Only one drain per queue runs at a time within a Gateway; a drain asked for while one is running makes it do one more pass. Delivery is at-least-once: a crash between a successful send and recording it re-sends that entry.
  - A send that hangs times out after 60 s, so it can't stall the drain. The timed-out send isn't repeated while it may still be running: if it later succeeds, the entry counts as delivered; if it fails, the entry is retried with the usual backoff.
  - A failed send is retried with exponential backoff (2 s, doubling, 8 attempts by default), so a short outage no longer dead-letters replies within milliseconds. An outage longer than about 4.2 minutes still dead-letters them, and nothing re-sends dead letters yet. Delivered entries beyond the newest 500 are pruned, except those that send an approved action: they stay as the record that the action was queued, and past the newest 500 their message text is dropped.
  - `mindstone approvals approve` records the decision before queuing, so a draft rejected while the confirm prompt was open is refused rather than queued (within the limits of #76, the approval store's own unlocked writes). If the queue is locked, the approval is undone and the action is pending again. An approval records whether its queue entry was written. If an approve is killed in between, approving it again (with the same confirmation) queues it. The check for an existing entry and the write happen under the queue's lock, so two approves at once, or an approve after the entry was written, add nothing. Approvals from before this change are never queued again. An approve records which process is queuing it, so a second approve while the first is still running is refused rather than treated as a killed one, and the queuing step re-checks the approval under the queue's lock. `mindstone approvals reject` refuses an action whose send is already queued, since rejecting it wouldn't stop it.
  - When a run failed, its error text (for example "model not available") was posted into the chat, including group chats. A failed run now posts nothing; the failure stays in the transcript and the connector's runtime status.
  - An empty reply still posts nothing, now covered by a test, and the connector smoke checks that replies go to the chat they answer.
- **App Engine runs scoped to an app, tenant or user no longer get the owner's context** (#70). Such runs went through as the owner, so a tenant's run carried the owner's `USER.md`, the memory index and owner-only invariants. They now get the non-owner treatment: no `USER.md`, memory index, owner-only invariants, handoff or onboarding seed, and in `pi-session` none of the owner's Pi resources. They keep their own scoped recall and rules marked `invariant_audience: all`. This covers both the gateway's `/agents/:id/runs` and the in-process `runMindStone` API. An App Engine run scoped only to the agent is still the owner's. A scoped run may use only session keys inside its own scope (a `403` or an error otherwise, so a tenant can no longer read or write the owner's main session), and an `appId`, `tenantId` or `userId` that is present but not a non-empty string (including `null`, or a value containing `:`) is refused rather than silently dropped. Whether a tenant run may recall the owner's unscoped memory is the open App Engine scope decision and is unchanged here.

- **Memory backfill keeps tenants apart and keeps non-owner turns out of the owner's recall** (#62).
  - Before this fix, `memory backfill` indexed every transcript with no labels. One App Engine tenant's run could surface in another tenant's recall, and a stranger's channel message could come back as the owner's memory.
  - Indexed transcript chunks now carry their surface, chat type, sender, audience and, for App Engine runs, the run's scope, taken from the entry itself, else its run, else the turn it follows (one scoped run in a session no longer affects the rest of it). A scoped run, reply included, is recalled only by a run whose recall scope matches every part of it, never by the owner's own recall. Scope is applied in the recall query itself, before ranking and before the candidate limit, so one tenant's volume can't crowd others out. App Engine runs at the tenant, app or user sharing level don't recall their own transcripts yet (their recall scope leaves out the agent id); that is part of the open App Engine scope decision.
  - Non-owner turns and the entries after them up to the next turn are not indexed unless `memory.transcripts.includeNonOwner` is set. Older connector entries without the new label count as the owner's only when they are a DM from one of the connector's `ownerSenders`; older email entries never do.
  - The next backfill removes transcript chunks that an earlier backfill indexed but the new rules exclude. It prunes nothing when the transcript directory is missing, empty or not a directory, and never touches memory files. Run `mindstone memory backfill` once after upgrading.
  - A scoped App Engine run no longer receives the owner's auto-compact handoff.
- **Channel turns that aren't the owner's direct messages no longer get the owner's context** (#61).
  - Before this fix, with the default `session.mode: "single"`, a group or channel message landed in the owner's main session. Its prompt carried the owner's recalled memories, `USER.md`, the memory index and the owner's earlier DM history.
  - **Upgrade step:** the owner is now named per connector with `channels.<id>.ownerSenders` (your own sender ids). Until it is set, nobody on that connector is the owner and your DMs there get no profile or memory; `mindstone doctor` warns. Being on `allowedSenders`, paired, or in an allowed domain lets someone talk to the agent but never makes them the owner.
  - Only a direct message from an owner sender that the connector can vouch for gets the owner's context. Every other turn (group, channel, thread, no chat type, unverified sender, another allowed sender's DM) runs in its own per-surface session, keyed by connector, without autoRecall, `USER.md`, the memory index or the auto-compact handoff. Only invariants marked `invariant_audience: all` reach it. In `pi-session` mode it also gets none of the owner's Pi extensions, skills, prompt templates, context files or built-in tools. The agent's `IDENTITY.md` still applies.
  - A message with no chat type is no longer treated as a DM: in a group it needs a mention or the trigger prefix, like any other group message.
  - Email: a From address is verified only when Gmail's own `Authentication-Results` header shows a DMARC pass for its domain (any other DMARC result is final) or a DKIM pass from that domain or a parent of it. A header with quotes, backslashes, unbalanced comments, two DMARC results or a result hidden in a comment is rejected, and a From header with two addresses is never verified. This authenticates the domain, not the mailbox.
  - Owner ids are compared trimmed and ASCII-case-insensitively; ids with non-ASCII characters never match.
  - Group history from before the upgrade stays in the main session; new group turns start their own sessions. In `per_surface` mode, the keys for group turns and other senders' DMs now include the connector, so those conversations also start fresh.
  - The owner's own surfaces (webchat, REST, OpenAI endpoints, App Engine) are unchanged. Session access by key with gateway auth `none` is a separate open decision.
- **pi-session turns no longer get Pi's built-in tools unless configured** (#54).
  - Before this fix, every turn in `pi-session` routing was offered Pi's built-in `read`, `bash`, `edit` and `write`. They run unsandboxed as the gateway user and bypass MindStone approvals.
  - Only the tools named in `routing.pi.builtinTools` are offered, and only Pi's default four can be re-enabled.
  - A guard refuses the turn before any model call if the session offers a built-in that wasn't enabled.

### Added
- **Skill Builder for the Console, and skills proposed in chat** (#104).
  - `GET /admin/skills`, `GET /admin/skills/<id>`, `POST /admin/skills/drafts`, `DELETE /admin/skills/drafts/<id>` and `POST /admin/skills/<id>/install` let an admin build a skill from a built-in or from scratch (id, label, description, goal, when to use it, outputs, safety notes, instructions), review the draft, and install or discard it. Installing needs the advanced-settings permission; drafting doesn't. Every write is audited.
  - Installed skills are now in the agent's prompt on the owner's turns: a `<mindstone-skills>` section in the route plan, next to identity and the memory index, for the Gateway (Console chat included) and `mindstone chat`. Each skill carries every field an admin reviews (label, description, goal, when to use it, outputs, safety notes) and its SKILL.md. The section holds 24,000 characters of skills; past that, a skill is listed by name and description only, and `GET /admin/skills` says so with `inPrompt: false`. Before, an installed skill was never used.
  - Asked in chat, the agent can draft a skill and propose it for install with a `mindstone-skill-proposal` block. The block becomes a pending `skill_install` approval; nothing is written until an admin approves it (`mindstone approvals` or the Console), which needs the advanced-settings permission. Approving installs it directly, without touching an admin's draft of the same id. Only the owner's replies propose one: a block in a reply to anyone else is stripped and dropped. `mindstone approvals show` prints the skill exactly as the agent will read it.
  - A proposal block (memory, calendar or skill) now ends at the first closing fence on a line of its own, so a proposal whose text holds a code block is no longer cut short.
  - Skills have a `goal` (`mindstone skill build --goal`).
- **Restart the gateway from the Console** (#90). `POST /admin/restart` restarts the gateway when whoever started it declared a supervisor (`MINDSTONE_AGENT_SUPERVISOR`) and the evidence matches; otherwise nothing exits and the answer says what to run on the host. `mindstone gateway start` and `mindstone gateway install` now declare theirs. A restart exits with 75 after a capped graceful shutdown; one at a time, at most 5 in 10 minutes. `GET /admin/status` adds `supervisor`, `startedAt` and `recentStarts`. See `docs/operations/GATEWAY_RESTART.md`.
- **Doctor and gateway logs for the Console** (#86). `GET /admin/doctor` returns the `mindstone doctor` report, with its network probes capped at 8 s so it answers inside the Console proxy's timeout. `GET /admin/logs?lines=N` returns the tail of the managed gateway log (1 to 500 lines, reading at most the last 512 KiB). Both mask credentials in text (URL credentials, `Authorization` values, `NAME=value` and JSON secrets).
- **Approvals from the Console** (#84). `GET /admin/approvals`, `GET /admin/approvals/<id>`, and `POST /admin/approvals/<id>/approve` or `/reject` let an admin decide proposed actions (connector sends, connector mutations, memory writes) from the Console, as `mindstone approvals` does. The approve and reject logic moved from the CLI into core, so both run the same guards: a decision made meanwhile is refused, a send is queued at most once, an approve still running is never repaired, and a send already queued can't be rejected. The list never carries draft text. Each decision is audited and recorded in the transcript as from the Console. The CLI's behaviour is unchanged.
- **Stored secrets listed and deleted from the Console** (#88). `GET /admin/secrets` lists them by name with their type, size, date, which connectors read them and whether one is a gateway credential; values are never read. `DELETE /admin/secrets/<name>` removes one under the same guards as replacing it: the advanced-settings permission, never a gateway credential, never a link made on the host, never through a link.
- **Model providers from the Console** (#38, P2 onboarding). `GET /admin/models` lists the provider presets, the providers already registered and Pi's models. `POST /admin/providers/<preset>` registers Ollama (local or Cloud), LM Studio or an OpenAI-compatible server in Pi's isolated `models.json`, with the key taken from a stored secret (escaped so Pi uses it as a literal) or an `*_API_KEY` environment variable (never from the request, never echoed), after listing the server's models with it. A hosted provider's address is fixed, and a local one must stay on this machine or a private network. It needs the advanced-settings permission. The gateway's own credentials (by name or value) and connector tokens can't be provider keys. `models.json` is now written atomically.
- **Admin API for the MindStone Console** (#38, P2). This is the server-to-server config API that the Console's settings and onboarding screens use.
  - It exists only when gateway auth is on and a separate admin credential is configured (`gateway.admin.tokenSha256`, recommended, which keeps only a digest on the gateway; or `tokenEnv`/`tokenFile`, at least 16 characters; never the gateway token). Only the Console server holds that credential; the ordinary gateway token is not enough. Calls also need the admin role. Gateway auth and the admin credential can only be changed on the gateway host.
  - `GET /admin/status` returns the onboarding state. `GET /admin/config` returns the config with every secret masked (inside objects, lists, header and environment maps, URLs and command-line lists) plus an `etag`. `PATCH /admin/config/<section>` applies a validated, atomic merge patch, judged against the config and permission at the moment it lands; `If-Match` refuses a stale write. What GET returned can be sent back unchanged; new secrets go through the secrets endpoint, never as plain config values.
  - `POST /admin/secrets/<name>` stores a new secret 0600 in a 0700 directory and never echoes it back. Replacing one needs the permission.
  - Only a short list of safe changes (model choice, bounded memory recall tuning, personas, and narrowing a channel's access) can be made without the advanced-settings permission. Everything else, including environment-variable references, URLs, paths, anything that lets someone new reach the agent, and who counts as the owner, needs an admin to grant the permission with an explicit confirmation. A grant lasts one hour and can be revoked sooner.
  - Every write and every refused write is audited with the user id. See `docs/gateway/API_REFERENCE.md`.
- **OpenAI-style server-sent events for chat completions** (#47). `POST /v1/chat/completions` with `stream: true` returns the reply as one content chunk, a stop chunk and `[DONE]`. It is not streamed token by token yet. Without the flag the JSON reply is unchanged.
- **Personas as models** (#47).
  - `/v1/models` lists `mindstone/<agentId>` for each configured agent.
  - A chat completion picks the agent from that model id when no `metadata.agentId` is given.
  - The gateway accepts `x-mindstone-user-id`, `x-mindstone-user-role` and `x-mindstone-conversation-id` from a front end. The user id becomes the sender, and the role and conversation id are saved on the transcript entries.
- **MindStone Console P0 spike** (#47, `spikes/console-librechat/`). This is a pinned LibreChat setup with the gateway as its only endpoint, plus a proxy that logs what LibreChat sends.
- **Memory: an always-in-force invariant tier** (#37).
  - Memories marked critical that have an authored `invariant` are injected every turn, whatever the query, instead of having to win a recall slot. If the budget runs out, an entry is cut to its name. Existing critical memories without an `invariant` are not included.
  - The memory index is injected every turn. When it doesn't fit, every entry is first cut to a bare pointer. Entries are dropped only if that still doesn't fit, and the prompt then says how many were left out.
